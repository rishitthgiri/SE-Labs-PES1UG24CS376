# Requirements Table — Digital Campus Library Reservation Gateway

## Functional Requirements

| ID | Type | Description | Priority | Acceptance Criteria | Rationale |
|---|---|---|---|---|---|
| FR-001 | Functional | The system shall allow a Student Member to search the catalog by ISBN, title, author, or keyword and return matching book records with real-time availability status (Available / On Loan / Reserved). | High | 1. Given a valid 10 or 13-digit ISBN, the system returns the exact matching catalog record within 2 seconds.<br>2. Given a partial title/author keyword, the system returns all matching records ranked by relevance.<br>3. Given a non-existent ISBN, the system returns a "No results found" message with zero matches.<br>4. Each result displays current availability status accurate as of the last completed transaction. | Students need a fast, reliable way to locate books and know availability before deciding to reserve or visit the library, reducing wasted trips and support-desk queries. |
| FR-002 | Functional | The system shall allow a Student Member to place a reservation (hold) on a book that is currently unavailable (On Loan or fully reserved), provided the member has not exceeded the maximum active reservation limit of 5 and does not already hold an active reservation for the same ISBN. | High | 1. Given availability = "On Loan" and active reservations < 5, a reservation request succeeds and the book status becomes "Reserved" for that member's position in queue.<br>2. Given the member already has an active reservation for the same ISBN, the system rejects the request with a "Duplicate reservation" error.<br>3. Given the member already has 5 active reservations, the system rejects the request with a "Maximum reservation limit reached" error.<br>4. A confirmation with a unique reservation ID and queue position is returned within 2 seconds of a successful request. | Reservations let students secure high-demand titles fairly instead of relying on repeated manual checks, while limits prevent hoarding and ensure equitable access. |
| FR-003 | Functional | The system shall maintain a First-In-First-Out (FIFO) waiting queue per ISBN, such that reservations are fulfilled strictly in the order they were placed, and each member can view their exact position in the queue. | High | 1. Given N existing reservations on an ISBN, a new reservation is assigned queue position N+1.<br>2. When a copy becomes available, the reservation with the lowest (earliest) queue position/timestamp is offered the book first.<br>3. If a member cancels a reservation, all subsequent members' queue positions are decremented by 1 automatically.<br>4. Queue position is visible to the member on demand and matches the placement timestamp order with 100% consistency (verified against timestamp sort). | FIFO ordering guarantees fairness — the student who requested first is served first — which is a core expectation of any library holds system and prevents disputes. |
| FR-004 | Functional | When a reserved copy becomes available for a member (i.e., their reservation reaches the front of the queue and a copy is returned or added), the system shall automatically send an availability notification (email and/or in-app) to that member within 5 minutes, and the hold shall remain valid for a 48-hour pickup window before expiring and passing to the next member in queue. | High | 1. Given a reservation reaches queue position 1 and a copy becomes available, a notification is dispatched within 5 minutes containing the book title, pickup deadline, and pickup location.<br>2. If the member does not check out the book within 48 hours of notification, the hold automatically expires and the copy is offered to the next queued member.<br>3. Notification delivery status (sent/failed) is logged for every event.<br>4. No notification is sent to members further back in the queue while an earlier hold is still active. | Timely notification with a bounded pickup window keeps the queue moving efficiently and prevents a copy from being held indefinitely by an unresponsive member. |
| FR-005 | Functional | The system shall support checking out (borrowing) and returning books, automatically calculate overdue fines for late returns at a fixed rate per day beyond the due date, and update the member's account and book availability accordingly. | High | 1. On checkout, a due date is set at loan date + 14 days and the book status changes to "On Loan."<br>2. On return, if the return date is after the due date, a fine of ₹5/day (configurable) is calculated and posted to the member's account, capped at ₹200 per item.<br>3. On return, book status updates to "Available" (or "Reserved" if a queue exists) within 1 minute.<br>4. Members with outstanding fines above ₹500 are blocked from placing new reservations or checkouts until the balance is cleared, and receive a clear error message stating the reason. | Automating checkout/return and fine calculation ensures consistent policy enforcement, reduces manual librarian effort, and gives members transparent, predictable accountability for late returns. |

## Non-Functional Requirements

| ID | Type | Description | Priority | Acceptance Criteria | Rationale |
|---|---|---|---|---|---|
| NFR-001 | Non-Functional (Performance) | The system shall respond to catalog search and reservation-status requests within 2 seconds under normal load (up to 500 concurrent users), and shall support at least 10,000 catalog records without degradation in response time beyond the stated threshold. | High | 1. Under a load test of 500 concurrent users performing search operations, the 95th-percentile response time is ≤ 2 seconds.<br>2. With a catalog of 10,000+ records, search response time does not exceed 2 seconds for 95% of requests.<br>3. System throughput sustains at least 50 requests/second without error-rate exceeding 1%. | Students and staff expect near-instant feedback during peak periods (e.g., start of semester); slow searches directly undermine adoption of the digital gateway over manual/in-person processes. |
| NFR-002 | Non-Functional (Security & Reliability) | The system shall authenticate all users via campus SSO credentials before allowing reservation, checkout, or account operations, encrypt all data in transit (TLS 1.2+) and at rest, and maintain 99.5% monthly uptime, with all failed login attempts and reservation/checkout transactions logged for audit purposes. | High | 1. Any attempt to place a reservation, checkout, or view account/fine data without a valid authenticated session is rejected with HTTP 401.<br>2. All client-server traffic is verified to use TLS 1.2 or higher (no plaintext endpoints reachable).<br>3. Measured monthly uptime over any rolling 30-day period is ≥ 99.5% (≤ ~3.6 hours downtime).<br>4. 100% of authentication failures and reservation/checkout/return transactions appear in the audit log with timestamp, user ID, and action type. | As a system handling personal member data and library assets, it must protect member privacy, prevent unauthorized access to accounts/fines, and remain dependably available since students rely on it during registration and exam periods. |

---
**Notes on consistency:**
- FR-002 and FR-003 together define the reservation + FIFO queue mechanism used in the Use-Case Specification (Section 3) and the `Place Book Reservation/Hold` use case in the UML diagram.
- FR-002's "Maximum reservation limit reached" and "Duplicate reservation" errors are the basis for the Alternate Flow in the use-case specification.
- FR-004 (notifications) is modeled as an `«include»`d use case (`Send Availability Notification`) invoked by `Place Book Reservation/Hold` fulfillment.
- FR-005 (overdue fines) is modeled as an `«extend»` of `Return Book`, triggered only when the return is late.
